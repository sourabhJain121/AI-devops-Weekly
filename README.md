# BMU Placement Assistant — RAG prototype

A grounded question-answering prototype: BMU placement documents go in, they are
chunked, embedded and stored in ChromaDB, and every answer is generated by a local
LLM through Ollama using only the retrieved text.

This is the **prototype stage** of the larger BMU Placement Intelligence system. It
implements the core pipeline (knowledge → retrieval → grounded answer). Resume/JD
analysis, the orchestrator, multi-model evaluation and Docker are not built yet.

## Pipeline

```
knowledge/*.pdf|md|txt
        |
        v
  text extraction        app/documents.py   (pypdf, page numbers preserved)
        |
        v
  section-aware chunking app/chunking.py    (800 chars, 120 overlap)
        |
        v
  embeddings             app/llm.py         (Ollama, nomic-embed-text)
        |
        v
  ChromaDB               app/vectorstore.py (cosine, persistent, with metadata)
        |
   ── query time ──
        |
  question -> query embedding -> top-k similarity search -> relevant chunks
        |
        v
  grounded prompt        app/rag.py
        |
        v
  Ollama / codellama:7b  app/llm.py
        |
        v
  answer + cited sources
```

## Requirements

- Python 3.11+
- [Ollama](https://ollama.com) running locally, with:
  ```
  ollama pull codellama:7b
  ollama pull nomic-embed-text
  ```

## Setup

```bash
pip install -r requirements.txt
cp .env.example .env          # optional; defaults work out of the box
```

## Add the knowledge

Put the official BMU placement documents (`.pdf`, `.md`, `.txt`) into
`knowledge/bmu/`, then delete `knowledge/bmu/SAMPLE_placement_policy.md` — that file
is **invented placeholder text**, present only so the pipeline can be demonstrated
before the real documents arrive.

Build the index:

```bash
python scripts/ingest.py --reset
```

Re-running is safe: a document's existing chunks are replaced, not duplicated.

## Run

```bash
python -m uvicorn app.main:app --port 8000 --reload
```

Open <http://localhost:8000>. Ask a question, and the right-hand panel shows exactly
which chunks the answer was built from, with document, section, page and score.

Or from the terminal:

```bash
python scripts/ask.py "What is the minimum CGPA requirement for placement?"
```

## API

| Method | Path | Purpose |
| --- | --- | --- |
| `GET`  | `/api/health` | Ollama reachability, active models, chunk/doc counts |
| `GET`  | `/api/documents` | What is currently indexed |
| `POST` | `/api/ingest` | Re-scan `knowledge/` and rebuild its entries |
| `POST` | `/api/upload` | Upload one document and ingest it immediately |
| `POST` | `/api/chat` | `{message, use_rag, top_k}` → grounded answer + sources |
| `POST` | `/api/retrieve` | Retrieval only — inspect what the LLM was given |

`/api/retrieve` exists so retrieval can be debugged separately from generation, which
is what makes the "was this a retrieval failure or a generation failure?" question
answerable.

## Design decisions

**Why RAG rather than a fine-tuned or plain model.** Placement policy is institution
specific, changes yearly, and must be quotable. Retrieval keeps the documents as the
source of truth and lets an answer point at the exact section it came from.

**Why section-aware chunking.** A chunk never crosses a heading. Policy documents are
written so each numbered section is a self-contained rule, so a heading is a real
semantic boundary — and it guarantees the `section` recorded on a chunk is the section
the text actually came from, which is what makes the citations honest rather than
decorative. Within a section, paragraphs are packed up to 800 characters so a rule and
its conditions stay together; only an over-long paragraph is hard-split, with 120
characters of overlap.

**Why ChromaDB.** Persistent, runs in-process with no server to operate, and stores
arbitrary metadata alongside each vector. That metadata (`source_type`, `document_name`,
`page`, `section`, `chunk_index`) drives the citations today and is what will later let
one company's JD be isolated from another's by filtering on the same field.

**Why embeddings come from Ollama.** The same runtime already serves the LLM, so there
is one dependency instead of two, and Chroma is never allowed to silently fall back to
downloading an embedding model of its own — every vector is passed in explicitly.

**How hallucination is limited.**
1. Chunks whose cosine distance exceeds `MAX_DISTANCE` are dropped before the prompt is
   built.
2. If nothing survives, the LLM is never called — a fixed "insufficient information"
   reply is returned, so the model cannot guess into a vacuum.
3. The system prompt forbids inventing rules, requires `[n]` citations, and requires
   advice to be labelled `Suggestion:` so it is never confused with policy.

**Why the LLM sits behind `app/llm.py`.** Model choice is one environment variable.
Swapping `LLM_MODEL` to another Ollama model changes nothing else in the pipeline,
which is what the later three-model comparison needs.

## Configuration

All settings are environment variables, listed in `.env.example`: `OLLAMA_URL`,
`LLM_MODEL`, `EMBED_MODEL`, `TEMPERATURE`, `CHROMA_DIR`, `COLLECTION`, `CHUNK_SIZE`,
`CHUNK_OVERLAP`, `TOP_K`, `MAX_DISTANCE`. Nothing environment-specific is hard-coded and
`.env` is git-ignored.

## Current limitations

- Single knowledge collection. Resume and company-JD source types are supported by the
  metadata but there is no per-company/per-session isolation yet.
- No orchestrator or intent routing — every question takes the same retrieval path.
- No eligibility rule engine, resume/JD matching or interview preparation yet.
- No evaluation harness, and no measured comparison across models.
- Not containerised.
- Retrieval is pure dense similarity; no reranking or keyword hybrid.
